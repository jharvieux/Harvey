M1-01 tenantClient UPDATE path does not sanitize tenant_id in the SET payload — latent cross-tenant write Medium BFTB 64 Likely
Security · M1 — Tenant isolation (write) · apps/main/src/lib/db/tenant-client.ts:90 · Open · V5·E4·S4
Evidence The tenantClient Proxy overrides tenant_id on insert/upsert (hardening the payload), but on UPDATE it only appends the .eq('tenant_id', ctx.tenant_id) WHERE filter and passes the SET payload through untouched. A handler that spreads untrusted input into .update() on a tenant-scoped table could set tenant_id to an attacker-named value, reassigning the row OUT of its tenant.
Impact Cross-tenant WRITE (row hand-off) if any update handler forwards client-controlled fields including tenant_id. The WHERE filter guarantees you can only update your OWN rows, but nothing stops the new tenant_id from pointing elsewhere. Mechanism certain; no confirmed exploitable call site was found in scope (hence Medium/Likely).
Fix In the UPDATE branch of the proxy, strip/override tenant_id in the SET payload the same way insert/upsert already do (defense-in-depth, one place). Optionally add a DB-level WITH CHECK on tenant-scoped update policies so the write is rejected server-side too.
When this is OK vs. not — confirm against your design:
✓ OK when Every update call site passes an explicit whitelist that excludes tenant_id.
✗ Not OK when Any handler spreads req.body into .update() on a tenant-scoped table.
