## READ THIS FIRST — nothing below is a capability number

Every count in this file is a **raw emission from an untriaged volume sweep**. No finding here has
been triaged, deduplicated across engines, or verified against the code it points at. An untriaged
finding is a **claim, not a fact** (#900 item 2, which owns the triage that changes that).

Concretely, that means:

- **No total is stated anywhere in this file, on purpose.** Not per module, not per severity, not
  across repos. A sum invites exactly the sentence — "Harvey found N issues across M repos" — that
  #900 item 2 forbids until triage completes. Per-target rows are given because a per-target row
  cannot be read as coverage; a sum can.
- This tier has **no baselines and asserts nothing about counts**. It cannot fail a CI check on a
  finding count — that is `corpus-drift`'s job over `src/scan/external-corpus.ts`'s *six different,
  graded* repos, and diluting that gate would be a real regression.
- Nothing here may be published, filed upstream, or quoted outside the repo. #900 item 4 is a
  separate operator sign-off that has not been given. Aggregate statistics are the publishable unit
  and even those are gated.

The structural guards that keep an ungraded row from reading as a scored one are asserted, not
promised: `src/scan/breadth-sweep.test.ts` now holds the line at the **manifest** (no gradeable
field, graded XOR ungraded) *and* at the **artifact** (`graded: false`, a self-naming `UNGRADED`
warning, no scorer-readable key, a `notRunTiers` list). All four assertions were exercised in both
directions on 2026-07-28 — green as committed, red against a mutated artifact.

## Mechanization feed and the recurrence rule

### Proposed rule for #900 item 3 — recurrence is counted in TARGETS, never in hits

#900 item 3 says the rule is undefined and that N hits inside one monorepo's workspaces is not N
repos. **This is my proposal for an operator ruling, applied consistently to everything above — not
a settled definition.**

1. A finding's **class** is `taxonomy :: rule-id`, where rule-id is the detector identity in the
   title's trailing parentheses, falling back to the title with paths, quoted strings and integers
   normalised out.
2. `repos(C)` = the number of distinct **manifest targets** in which C fired at least once. **One
   target is one repo pin and counts once**, however many workspaces, packages, files or lines fired
   inside it. A 40-workspace monorepo contributes exactly 1.
3. `hits(C)` (total emissions) and `maxInOne(C)` (largest single-target count) are a **separate
   axis** and are never folded into `repos`. This is the whole point: it keeps the cal-diy M5 row
   (2,569 hits, one repo) out of the mechanization feed and in the over-fire list, where it belongs.
4. **Mechanization candidate:** `repos(C) ≥ 8` (a majority of 15) *and* C currently needs the
   semantic tier. **Over-fire candidate:** `maxInOne(C) ≥ 100` *and* `maxInOne(C)/hits(C) ≥ 0.5`.

**Known bound on this rule, stated rather than discovered later:** "distinct repo" is not "unrelated
codebase". Several Bucket A targets are Supabase SaaS starters that may share template ancestry, so
two targets can be substantially the same code and inflate `repos(C)` without being independent
evidence. Not measured here. If the operator wants recurrence to mean *independent* recurrence, the
rule needs a same-ancestry check the sweep does not currently perform.

## Drift against 2026-07-24 — same pins, so every delta is a Harvey change

The pins are unchanged, so the source trees are byte-identical to the prior run. **Every difference
below is caused by 183 commits of Harvey, not by the targets.** This is the most useful thing a
pinned re-run produces and it has no equivalent in the graded corpus, which measures against fixed
baselines rather than against its own past.

Two deltas want an explanation and neither is triaged here:

- **`hexclave` M4: 12 → 1390.** A 116× change on an identical tree. Either M4 was broken on hexclave
  before and is now working, or it has started firing on something it should not. Nothing in the
  graded corpus would have caught either.
- **M9 fell on 7 of 15 targets** against unchanged trees: onlook 89→13, hexclave 157→60, grida
  138→94, priceai 111→75, liam 33→19, open-scouts 15→10, elatoai 5→3. It rose on none. A
  broad-but-quiet reduction in a module's emissions across unrelated repos is the "a detector
  stopped firing" shape, and no count-based gate covers M9. This is the single most important
  follow-up in this file after #1451.

Neither is a conclusion — both are questions this run is able to ask because the pins held.

## FP candidates — PROPOSED ONLY, not written

`briefs/fp-rules.txt` is functional tool input, not a supervised doc path (CLAUDE.md, operator ruling
2026-07-24), but #900 item 5 says candidates are **proposed, never auto-applied**, so nothing was
written. These are shapes flagged by volume and concentration, **not by verification** — no finding
below was read against its source line, which is exactly the triage #900 item 2 owns:

1. **`gha-workflow-env-secret` — 222 hits in cal-diy, 2 repos.** An upstream (non-`harvey-*`)
   semgrep rule firing at Medium on GitHub Actions workflow YAML. Harvey's scope is application code;
   `.github/workflows/**` is arguably the infrastructure-out-of-scope boundary (#903), which would
   make this an `INFRA-SCOPE-00` disclosure rather than 222 Medium findings.
2. **`generic-api-key` — 187 hits in cal-diy, 9 repos, High.** A generic-entropy secret rule at High
   severity across nine repos is the classic secret-scanner FP profile. Worth checking whether these
   survive the verified-credential filter or are riding the review tier.
3. **Env var read but not declared in env schema — 202 hits in cal-diy, 7 repos.** In a monorepo
   each workspace has its own env schema; a repo-root-relative check would report every workspace's
   vars as undeclared. Candidate shape: scope the check per workspace.
4. **M5 single-use helper — 15/15 repos, median 210/repo.** Fires everywhere at high volume. Not
   wrong per se, but at this density it is a rollup candidate (#935's shape) rather than N findings.
5. **The Prisma PK-without-tenant-scope rows (1,108 across 3 repos, High).** Listed here as the
   *first thing to triage*, explicitly **not** as a proposed FP rule — it may be entirely correct.
   Volume alone is not evidence either way, and calling it an FP before reading it would be the same
   error as calling it a capability number.
