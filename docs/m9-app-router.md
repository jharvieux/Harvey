# M9 — server→client boundary & rendering

Detector: `src/detectors/app-router.ts` (`detectAppRouterFindings`). Brief: `briefs/scan-extras.txt`
(M9 section). Tests/fixtures: `src/detectors/app-router.test.ts`, `src/detectors/__fixtures__/`.

> **M9 is no longer Next-only (#916/#917/#918).** The checks below are written against Next.js App
> Router, which is still the default and best-covered path, but `detectAppRouterFindings` now routes
> through a **framework-agnostic boundary model** (`src/detectors/boundary-model.ts`): a target
> detected as **Remix** or **React Router 7** runs the shared `remix-adapter.ts` (RR7 absorbed
> Remix's loader/action model), and **TanStack Start** runs `tanstack-adapter.ts`
> (`createServerFn`). The **portable** boundary checks run through the adapter's own idioms — five of
> them (`remix-adapter.ts` / `tanstack-adapter.ts`, `*_SUPPORTS`): server→client leak, server-mutation
> authz, server-mutation input validation, SSR-only browser-API misuse, data-fetching waterfall. The
> remaining checks are Next-App-Router-specific (client-supplied owner id, route segment config, the Full Route Cache and the
> cache-bleed shapes, `<Suspense>`/PPR, the `server-only` poison pill, the `route.ts` convention,
> unbounded/self-calling routes and uncapped retry/fan-out) and
> each draws an explicit `notAssessedCheckNote` row on those frameworks — partial coverage stated,
> never silently upgraded to full. **Astro, SvelteKit and Nuxt have no adapter
> yet** (#920/#921): they fall through to the #872 not-assessed note, an Info row that names the
> framework, never a silent Next-premise run. Where a section below says "App Router," read it as
> "the Next adapter's shape of this check." Falsify with `pnpm detect-static <a-remix-target>`.

## Method

Static AST analysis over TypeScript/TSX source using the TypeScript compiler API
(`typescript`, already a devDependency — `ts-morph` is not present in this repo, so no new
dependency was added). `detectAppRouterFindings(files: { path, text }[])` parses every file with
`ts.createSourceFile` and runs each check below over the resulting ASTs, emitting `Finding[]`
(`src/findings.ts`). The server→client leak check needs sibling files (to know which imported
components are Client Components), so callers should pass the project's full relevant `.ts`/`.tsx`
source set, not one file at a time.

Findings route into §3 (security) for the HIGH M9-tagged checks — server→client data leak, missing
`server-only` guard, server-mutation missing input validation, unsafe route segment config,
cross-user cache bleed — and §3b (performance) for the MED/LOW ones (missing cache config,
data-fetching waterfall, accidental dynamic rendering, conflicting route segment config,
unbounded/self-calling route, uncapped retry/fan-out, SSR-only API misuse, missing Suspense
boundary, SPA missing root error boundary), tagged with a `taxonomy` beginning `M9 —`. (The Server
Action missing-auth check AND the client-supplied-owner-id check are both generated by this same
detector but tagged `M1 —` as of #231/#465 — see those sections below.)
All findings default to `status: "Open"` and a generated `id` of the form `M9-01`, `M9-02`, ...
(sequential per detector run — re-numbered, not stable, across runs with a different file set).

## Router detection (Pages vs App Router)

Before running the App-Router-only checks, `detectAppRouterFindings` classifies the file set: a
project with any file under an `app/` directory is treated as (at least partially) App Router; a
project with a `pages/` directory (excluding `pages/api/`) and **no** `app/` directory at all is
Pages-Router-only. On a Pages-Router-only project the missing-`server-only`-guard check is skipped
entirely — Next already strips non-`NEXT_PUBLIC_` env vars from the Pages Router client bundle at
build time, so the guard is moot there, not missing. (**#231:** this closed a guaranteed false
positive — the check previously fired on every Pages Router target, e.g.
`boxyhq/saas-starter-kit`.)

## Checks

### Server → Client data leak — HIGH (`M9 — Server→client data leak`)

**Detects:** a non-`'use client'` file that (a) imports a component from a sibling file whose
leading directive is `'use client'`, (b) holds a variable bound to a raw Supabase query result
(`const { data: x } = await ...from(...).select(...)`, or the identifier form), and (c) passes that
variable whole into the client component — either `<Comp data={row} />` or `<Comp {...row} />`.

**Detection method:** AST. Client-component identity comes from the imported file's leading
directive. Import resolution follows both relative specifiers (`./Foo`, `../lib/Foo`, with
`.ts`/`.tsx`/`index.ts(x)` resolution) **and configured path aliases** — the tsconfig/jsconfig
`compilerOptions.paths` wildcard entries and the create-next-app `@/*`→root default (#380, via
`resolveImport`/`collectPathAliases`). A leak through an aliased import (`@/components/Foo`) IS
followed; only an *unconfigured* or computed/dynamic specifier is invisible to resolution and would
be a **false negative**. A prop is only flagged when the *whole* query-result variable is passed;
`<Comp data={row.name} />` (a narrowed projection) is correctly treated as safe. One hop of
aliasing IS tracked (#847): a leak through an intermediate binding (`const dto = row; <Comp
data={dto} />`), a spread binding (`const dto = {...row}`), or an inline spread (`<Comp
data={{...row}} />`) still flags. **Known false negative:** a leak laundered through more than one
hop, or through an object literal that spreads only a *nested* field (`<Comp data={{...row.x}} />`),
is not tracked.

### Missing `server-only` guard — HIGH (`M9 — Missing server-only guard`)

**Detects:** a file that reads a secret-shaped `process.env.*` variable (name matches
`SERVICE_ROLE`, `SECRET`, `PRIVATE_KEY`, `API_KEY`, or `TOKEN`, excluding `NEXT_PUBLIC_*`), has no
`import "server-only";`, **and** — the #231 gate — is actually reachable from a `'use client'` file
through the relative-import graph. This is the enforcement side of the leak check: a shared module
like this can be transitively pulled into a Client Component bundle with no build error, but only
if something on the client side actually imports it.

**Detection method:** AST for the env-access and import-declaration checks; exempts `route.ts(x)`
and `middleware.ts` files (these are already server-exclusive by Next.js's own routing convention,
so requiring the guard there would just be noise), files under a `'use client'`/`'use server'`
directive (a `'use server'` module is already guaranteed server-only by the Next compiler), and any
project detected as Pages-Router-only (see "Router detection" above). The real-client-import-path
check builds a relative-import graph from every `'use client'` file and only flags a module that's
transitively reachable from one of them: a 6-repo triage (#231) found every prior raw hit was
already shielded by the `next/headers` barrier or the `'use server'` boundary with nothing on the
client side importing it, so gating on a real reachable path — not a new name heuristic — was the
fix. **Known false positive:** the secret-name pattern is still a heuristic — an env var that
happens to match (`FEATURE_FLAG_API_KEY_ENABLED`) but isn't actually sensitive will still be
flagged if a real client-import path exists; a human should confirm before reporting. **Known false
negative:** secrets referenced only through a re-exported constant (`import { SERVICE_ROLE_KEY }
from "./config"`) rather than `process.env` directly aren't traced back to their source. The
client-import-path graph follows both relative specifiers **and configured path aliases** (the
tsconfig/jsconfig `paths` wildcards and the `@/*` default, #380), so a client-import path through
`@/lib/foo` IS seen — only an unconfigured or computed specifier escapes the graph.

### Server Action missing auth — retagged to M1 (`M1 — Server Action missing authorization check`)

**Detects:** a Server Action (file-level `'use server'`, or a function whose body opens with an
inline `'use server'` directive) that calls a DB mutation (`.insert(`, `.update(`, `.upsert(`,
`.delete(`, or `.rpc(`) with no auth/session pattern (`auth.uid`/`getUser`/`getSession`,
`getServerSession`, `getCurrentUser`, `requireAuth`/`requireUser`/`requireSession`,
`assertPermission`/`assertAuthorized`, `checkAuth`, `verifySession`, or a bare `auth()` call)
anywhere in the action's body.

**#231:** a 6-repo triage put M9's rendering checks at ~0% precision (26 raw → 3 real), and the 3
real hits were all this check — a Server Action with no visible auth check is a
broken-function-level-authorization finding (the same class #221 catalogs), not an App-Router
*rendering* issue. The detector still lives in `src/detectors/app-router.ts` (it shares the
Server-Action/mutation-call AST work with the input-validation check below), but its `taxonomy` is
now `M1 — Server Action missing authorization check` — route it into §3's authorization section,
not this module's §3b/§3 M9 rows.

**Detection method:** AST to locate Server Actions and confirm the mutation call; the auth check
itself is a text-level pattern match over the action's source range (a real authority check that
uses a different name than the ones above is a **false negative** — the list isn't exhaustive.
Conversely a comment or unrelated string that happens to contain one of these words would be a
**false positive**, though that's unlikely in practice). Only scoped to actions that call a
mutation — a read-only action with no auth check is intentionally not flagged by this check (that's
a different, lower-severity gap not covered here).

### Server Action missing input validation — HIGH (`M9 — Server Action missing input validation`)

**Detects:** the same mutating Server Actions as above, flagged when the body has no schema-parse
call (`.safeParse(`, `.parse(` — excluding `JSON.parse(` — or a bare mention of `zod`, `valibot`,
`yup.`, or `ajv`).

**Detection method:** same text-level pattern match, same scope (mutating actions only). **Known
false positive:** validation performed by a helper function whose name doesn't match the pattern
(`const input = sanitize(formData)`) isn't recognized. **Known false negative:** a schema `.parse`
call that validates the *wrong* shape (e.g. parses `name` but not the `tenant_id` actually used in
the mutation) still satisfies the pattern — this check proves *a* parse call exists, not that it
covers every field trusted from the client.

### Unsafe / missing cache config — MED, best-effort (`M9 — Unsafe/missing cache config`)

**Detects:** a `page.tsx`/`layout.tsx` file that runs a Supabase `.from(...).select(...)`
query with no cache signal (`unstable_cache`, `"use cache"`, or a `revalidate` reference) anywhere
in the file. The check is suppressed if the file reads any dynamic API that forces rendering per-request
(`cookies()`, `headers()`, `noStore()`, `unstable_noStore()`, or direct `searchParams` access) — such a
route is dynamic by construction, so a missing cache config is expected and not flagged. **#231:**
also suppressed when the file itself checks the caller's session/auth (the same auth-pattern match
the Server Action auth check uses) or sits on an auth/token-gated route segment (`login`, `signin`,
`signup`, `register`, `reset-password`, `forgot-password`, `verify`, `invite`, `magic-link`,
`callback`, `auth`, …) — a 6-repo triage found every prior hit here was an auth page, a theme
cookie, or a token-gated viewer: legitimately per-request, never a static/ISR candidate.

**Detection method:** file-level text heuristic, deliberately light per the brief. It covers only the
cost-side "never cached" mode; the isolation-side mode (a cache directive that IS present but shared
across users) is a separate check — see *Cross-user cache bleed* below. **Known false positive:**
caching applied one layer up (a cached data-access function imported into this file) won't be visible
from this file's text and will still be flagged.

### Cross-user cache bleed — HIGH (`M9 — Cross-user cache bleed`)

**Detects (#1051):** the brief's *other* cache failure mode — a cache configuration that lets one
user's content bleed to another. The missing-config check above treats **any** cache signal as
evidence of correctness (`CACHE_SIGNAL_PATTERN` → skip) and any auth read as evidence the route is
per-request, so before #1051 the presence of the very directive that causes the bleed is what
stopped Harvey reporting it — the dangerous direction failed silently. Three shapes:

1. `unstable_cache(cb, keyParts, opts)` whose cached callback is per-user — it takes a
   user/tenant/org-shaped parameter, or reads the caller's session inside the cached function —
   while the cache **identity** (key parts + `tags`) carries no per-user component. One global
   entry: whoever populates it first has their rows served to everyone else.
2. A `"use cache"` scope that resolves the caller's identity **inside** itself. A cached scope is
   keyed on its arguments, so the identity read is invisible to the key. (The mirror-image shape —
   the identity arriving as an argument — is the *correct* one under `use cache` and is not flagged.)
3. An auth-gated `route.ts`/`middleware.ts` returning `Cache-Control: public` or `s-maxage` with no
   `private`/`no-store` — the shared CDN caches an authenticated response.

**Detection method:** AST for the `unstable_cache` call sites and the `"use cache"` directive
prologues; a text match for the `Cache-Control` value. Unlike the three Supabase-shaped data-layer
checks this one keys on the auth + cache signals rather than `.from().select()`, so it stays live on
a Prisma/Drizzle/raw-SQL target. **Disclosed limitation:** `unstable_cache(importedFn, …)` — a
callback defined in another module — cannot be adjudicated from this file, so those call sites draw
an explicit `M9 — Cross-user cache bleed — not assessed` row naming them rather than being dropped.
Fixtures: `src/detectors/__fixtures__/cache-bleed/{positive,negative}`; corpus entries
`M9C-CACHE-BLEED-POS`/`-NEG`.

### Data-fetching waterfalls — MED, best-effort (`M9 — Data-fetching waterfall`)

**Detects:** two `const { data: x } = await ...from(...).select(...)` (or plain-identifier) query
declarations back-to-back in the same block, where the second's statement text doesn't reference
any name bound by the first (i.e. it isn't obviously reading the first query's result).

**Detection method:** AST for locating the two declarations; the dependency check is a substring
match against the first declaration's bound name(s), not a data-flow analysis — a dependency
expressed indirectly (e.g. through a helper function call) would be a **false positive** (flagged
as independent when it isn't). Only checks directly-adjacent declarations in one block; queries
separated by other statements, or split across nested blocks/branches, aren't compared (**false
negative**). Emits at most one finding per function to avoid pile-on noise on functions with more
than two queries.

### Accidental dynamic rendering — MED, best-effort (`M9 — Accidental dynamic rendering`)

**Detects two patterns, both scoped to `page.tsx`/`layout.tsx` files only:**
1. A direct call to `headers()`, `cookies()`, `noStore()`, or `unstable_noStore()` anywhere in the
   file.
2. The page's default-exported component destructuring a `searchParams` prop and then reading a
   field off it directly (property/element access, `await`ing it, or destructuring it) rather than
   only forwarding the whole object to a child component.

**Detection method:** AST. Pattern 2 deliberately treats "receives `searchParams` as a prop" as
fine and only flags an actual *read* — passing the object through untouched to a `<Suspense>`-
wrapped leaf (the brief's recommended fix) is correctly treated as safe. **Known limitation:**
because each file is analyzed independently, this can't see whether a *child* component (in another
file) reads `searchParams`/calls `headers()` high in the tree outside a Suspense boundary — the
brief's "read high in the tree" is approximated as "read in this route's own module," not a real
call-graph position. A leaf component that itself calls `cookies()` outside Suspense, one import
away, is a **false negative** here.

### SSR-only API misuse — LOW, best-effort (`M9 — SSR-only API misuse`)

**Detects:** a read of a browser-only global (`window`, `document`, `localStorage`,
`sessionStorage`, `navigator`) that executes on the SSR render path — module top level, or a
component/module-level helper's render body in a `.tsx`/`.jsx` file — with no SSR guard.

**Detection method:** AST. "On the render path" is a nearest-enclosing-function test (#964/#1460):
0 enclosing functions (module top level) or exactly 1 in a JSX file (a component, or a module-level
helper reached from the render path — resolved recursively by its own in-file call sites) is on
path; a class member (method/accessor/constructor — an OO lifecycle method, not the App Router
render path), a plain `.ts`/`.js` module's free function (no component can live there), a
`clientLoader`/`clientAction` export or a `createClientOnlyFn`/`createIsomorphicFn().client(...)`-
wrapped callback (Remix/RR7/TanStack's own "never runs on the server" markers, #1293/#1276), and
anything nested ≥2 functions deep (an effect callback, an event handler) are all off path and never
flagged. **The FP guards PR #466 wrote down, stated as they behave, not aspirationally:**
- silent inside a `useEffect`/event-handler/callback body — off path because it's ≥2 functions deep,
  not because of any name-based recognition of "useEffect";
- silent behind a `typeof window !== "undefined"` (or the other four globals) guard, matched both as
  an enclosing `if`/ternary/`&&`/`||` condition and as a PRECEDING sibling `if` that exits
  (`return`/`throw`) before the read (#1293 — an ancestor-only walk missed the early-return form);
- silent behind an optional-chained access (`window?.x`) or an enclosing `window?.x` condition
  (#964) — treated as the author's own signal the global may be absent;
- silent on a **shadowing local** — any name bound anywhere in the file (import, parameter,
  variable/function/class declaration, including a destructured binding, #1293) that shares a
  browser global's name is read as that local, not the DOM global;
- silent inside a class-member method — the measured proposit Lexical `createDOM` false positive
  (#1460): a class lifecycle method is not on this check's render path.

**Known false negative:** a helper reached only through an OUT-OF-FILE call site is conservatively
left flagged rather than resolved — the call-site graph this check builds is in-file only.

### Unbounded / self-calling route or edge fn — MED (`M9 — Unbounded/self-calling route or edge fn`)

**Detects two shapes, both scoped to server request handlers** (`route.ts(x)`, `middleware.ts`,
`pages/api/*`, or any file that declares `export const runtime = "edge"`):
1. An always-true loop header (`while (true)`, `while (1)`, `do … while (true)`, `for (;;)`) whose
   body contains no `break`/`return`/`throw` anywhere.
2. A `fetch(...)` call whose argument subtree reads the incoming request's own URL
   (`request.url`/`req.url`, or anything off `.nextUrl`) — the handler calling back into itself.

**Detection method:** AST. Pattern 1 is deliberately conservative toward silence: any
`break`/`return`/`throw` anywhere in the body counts as an escape, even one that actually only
terminates a *nested* loop — a false negative, never a false positive. Pattern 2 recognizes only
`request`/`req`-named receivers.

### Uncapped retry/fan-out — MED (`M9 — Uncapped retry/fan-out`)

**Detects two shapes (#1262), the same route/edge-handler scope as the check above:**
1. A retry loop (`for`/`while`/`do…while` whose body makes an outbound call inside a `try`/`catch`)
   whose HEADER resolves to no literal/const bound — `while (true)`, `while (!done)`, or a `for`
   condition not provably capped by a numeric literal or a file-local `const`.
2. `Promise.all(xs.map(cb))` / `Promise.allSettled(...)` where `cb` makes an outbound call and `xs`'s
   root identifier is derived from the incoming request (a handler parameter, or a variable bound
   from a `request`/`req`/`searchParams`/`params`/`.body`/`formData` read, resolved transitively
   through further local assignments), with no `.slice(...)`/`.splice(...)` bound anywhere in the
   mapped expression's receiver chain.

**Detection method:** AST, reading only the loop HEADER and the mapped expression — never the loop
body or any other code in the handler; both scope statements appear in the finding's own evidence,
not only here. **Disclosed limitation, with the population MEASURED on the target it runs against**
(`M9 — Uncapped retry/fan-out — scope`, an Info row emitted whenever the target has any route/edge
handler at all, naming its own count for each): four sub-shapes this pass does not reach — retries
delegated to a retry/backoff/concurrency library (the cap lives in a config object this pass doesn't
read); a fan-out over a collection this pass does not tie to the request, typically an unbounded DB
read (left unflagged to hold precision, not silently dropped); retry by RECURSION, a helper calling
itself on failure rather than a loop (no loop node exists to bound); and a loop whose real cap lives
in the BODY rather than the header — a counter incremented then `break`-ed on, a flag the `catch`
sets — which this pass reports as uncapped rather than guessing it's bounded (the fail-loud
direction, #1440).

### Unsafe route segment config — HIGH (`M9 — Unsafe route segment config`)

**Detects:** a `page.tsx`/`layout.tsx`/`route.ts(x)` file (excluding `'use client'` files) that sets
`export const dynamic = "force-static"` while it also reads a dynamic API (`cookies()`, `headers()`,
`noStore()`, `unstable_noStore()`, or direct `searchParams` access) or checks the caller's
session/auth (the same auth-pattern match the Server Action auth check uses).

**Detection method:** AST for locating the `export const dynamic`/`revalidate` declarations — only
string/numeric/boolean literal initializers are recognized, so a computed or re-exported value is a
**known false negative**; text-pattern reuse of the dynamic-API and auth detection already used
elsewhere in this module.

### Conflicting route segment config — MED (`M9 — Conflicting route segment config`)

**Detects:** the same file set as the check above, flagged when `dynamic` and `revalidate` are set
to values that cancel each other: `dynamic = "force-dynamic"` with a positive `revalidate`
(revalidate is dead — force-dynamic never caches), or `dynamic = "force-static"` with
`revalidate = 0` (force-static caches indefinitely, `revalidate = 0` means always-revalidate).

**Detection method:** AST, the same declaration-collection pass as the check above. Only these two
literal-value combinations are recognized; a conflict expressed through a non-literal or an
indirect binding is a **false negative**.

### Missing Suspense boundary — LOW, best-effort (`M9 — Missing Suspense boundary`)

**Detects:** a `page.tsx`/`layout.tsx` file (excluding `'use client'` files) that reads a dynamic API
AND awaits a data-fetch (a Supabase query chain, or a bare `fetch(...)`) with no
`<Suspense>`/`<*.Suspense>` JSX element anywhere in the file.

**Detection method:** AST. Deliberately narrow: it fires only when a dynamic read and an async fetch
co-occur with zero `<Suspense>` usage anywhere in the file, so a boundary present anywhere in the
file — even one that doesn't demonstrably wrap the dynamic subtree — suppresses the finding, a false
negative preferred over flagging a file that already uses Suspense somewhere. **Known false
negative:** a `<Suspense>` boundary placed in a *different* file (a child component) is invisible to
this per-file check — the same call-graph limitation the Accidental dynamic rendering check above
discloses.

### Client-supplied owner id — retagged to M1 (`M1 — Client-supplied owner id trusted by authenticated action` / `M1 — Client-supplied owner id trusted by unauthenticated service-role action`)

**Detects:** a Server Action / route action / server function — portable across the Next, Remix/RR7
and TanStack adapters as the boundary model's `client-owner-id` check — that mutates rows using an id
traced back to the action's own arguments (a parameter, or a binding derived from one within one hop
of destructuring/spreading) rather than to the session it authenticates: either in an
`.eq("<owner-column>", …)` filter on a service-rooted client, or in an `insert`/`upsert` object
literal's owner-shaped column. Two variants, one finding class: (a) the action DOES authenticate the
caller (binds a session) but never compares the session's identity against the client-supplied id
before mutating; (b) the action makes NO auth call at all and runs on the service-role client (RLS
bypassed) — raised HERE rather than also by the missing-auth check, because #465's dedupe treats it
as one defect, not two.

**Detection method:** AST dataflow-lite. Tracks client-rooted names (action parameters plus one hop
of derivation) forward to an `.eq(...)`/insert-column site; a name bound from
`getServerSession`/`requireAuth`/etc., or from a value the server itself fetched from the DB, is
treated as authoritative rather than client-supplied, and an explicit comparison between the two
anywhere in the body clears the finding. `precisionTier: "review"`, never free-count: the AST proves
the value is client-rooted and that no in-body comparison exists — not that authorization is absent
from a wrapper/middleware outside this file, which is left for triage. **Known false negative:** an
authorization check enforced entirely in a wrapper/middleware this file doesn't show is invisible to
this check.

### SPA missing root error boundary — LOW, best-effort, SPA-only (`M9 — SPA missing root error boundary`)

**Detects:** on a confirmed non-Next SPA (Vite, or an unrecognized `other` framework — whole-target
or one Vite workspace of a monorepo, #627/#597) — the one M9 check that DOES apply there even though
the rest of the App-Router family is suppressed to the non-SSR-SPA coverage note — a React root mount
(`createRoot(...).render(<jsx>)`, or `ReactDOM.render(<jsx>, el)` for React 17) with no error boundary
anywhere in the scanned scope: no class defining `componentDidCatch`/`getDerivedStateFromError`, no
`react-error-boundary` import, no `<...ErrorBoundary>` JSX element, no `withErrorBoundary(...)` call.

**Detection method:** AST, scoped to the files passed in (the whole target, or one Vite workspace's
files in a monorepo). Precision errs toward silence: ANY recognized boundary form anywhere in scope
suppresses the finding, even one that doesn't demonstrably wrap the mounted root — a false negative
preferred over flagging an app that already guards itself somehow.
