# Harvey Calibration Corpus Spec — True Positives + False-Positive Lookalikes

Status: research draft (2026-07-08) · Drives issues #52 (FP catalog / suppression), #61 (corpus fixtures), #9 (calibration target).

## Intro

Harvey's free "quick scan" surfaces a **count** of issues, so a single wrong "Critical" is credibility-fatal (see `docs/design/mechanical-toolchain.md` §5, §7). The true-positive half of the picture already exists: `docs/design/scan-coverage-gaps.md` is a ranked, sourced catalog of the most common Next.js/Supabase vulnerabilities, tagged MECHANICAL vs DEEP. This spec supplies the **missing half** — the most common *false positives* that competing SAST/lint/secret tools throw on JS/TS/React/Next.js/Supabase code — and then merges both halves into one build spec (Task B) for expanding `targets/calibration/` and gating rules.

The rule for promotion is unchanged from `mechanical-toolchain.md` §7: a rule enters the free count only at ~100% corpus precision. Every NEGATIVE row below is a benign lookalike the corpus must contain so we can *measure* that precision — a rule that fires on any NEGATIVE row is demoted to LLM-triage or suppressed.


**Addendum, 2026-07-27 (#1344) — the code was looser than this rule for a long time, and it cost a
release.** The sentence above says "a rule that fires on any NEGATIVE row is demoted or suppressed."
`scoreEntry` did not enforce that: a negative passed on `!highFlagged` alone, so a rule firing on a
benign lookalike at REVIEW tier scored `cleared from the count (review-tier hit only, triaged out)`
and no gate in the repo could fail on it. #1251 hit exactly that shape (a widened taint source made
`harvey-path-traversal` fire on `N-STORAGE-DB-PATH`) and it surfaced only because someone hand-diffed
`dry-run/findings.json`; on the same day three detector regressions reached `main` with both scored
gates green.

The gap is closed as a RATCHET rather than a ban, because the looseness was not arbitrary: 28
negatives legitimately draw review-tier noise, which is precisely what the free-count exclusion
exists to triage out, and failing on all of them would say nothing about movement. `CorpusEntry.
reviewTierHits` now records the taxonomies each negative is MEASURED to draw, and any UNRECORDED
review-tier taxonomy fails the gate naming it. `validate-calibration.ts` carries a negative control
that replays #1251 against `N-STORAGE-DB-PATH` and must print `ratchet FIRED`, so a green run means
"passed AND can still fail." The 28 were populated from a measured run, not asserted from memory.

The heuristic (M7/M8) corpus has the sibling problem and the sibling fix: a negative fixture
directory the scanner never read reports zero exactly like one it scanned and cleared.
`HeuristicEntry.scopeControl` names a known-caught hit planted in that directory — excluded from the
false-positive count, and the row FAILS if it does not fire.

Two scoping notes carried from the source docs, so we do not over-claim:
- **Structural / cross-tenant RLS logic is NOT mechanically detectable.** `USING (true)` and `USING (auth.role() = 'authenticated')` (calibration bugs #1, #2) are enabled policies that *look* correct — only reading the policy body catches them. The Supabase Advisor (`get_advisors`, Splinter lint `0013 rls_disabled_in_public`) catches RLS *disabled* (bug #3), but not a permissive-but-present policy. Replay (#5), counter race (#6), and unscoped cross-tenant `.update()` (#7) are likewise semantic/dynamic. These belong to the DEEP / connected-advisor / dynamic tiers, not the mechanical free count.
- **Existing repo assets to reuse, not re-derive:** `briefs/fp-rules.txt` already suppresses several benign classes (service-role legitimate server use, RLS-enabled-no-policy on a service-only table, in-memory `Map`-as-cache, operator/env config URLs, test/fixture scope, documented exceptions). `src/scan/rules/semgrep-nextjs-supabase.yml` already ships rules for `dangerouslySetInnerHTML`, permissive CORS, service-role-in-client, and open-redirect. Rows below cross-reference these rather than duplicating them.

## Task A — The false-positive catalog (grouped by tool)

Each entry: the tool + rule, the benign pattern it wrongly flags, why it's benign, and how Harvey should avoid it.

### A.1 — `eslint-plugin-security` (heuristic; ~1:1 TP:FP — `mechanical-toolchain.md` §5 already recommends dropping it from the free count)

- **`detect-object-injection`** — flags *any* `obj[expr]` bracket access regardless of context. Benign whenever the key is a hardcoded/enum-constrained/validated value (a lookup table, a switch over known keys, indexing a typed array). The rule "detects a very serious vulnerability but flags safe code that merely looks similar" and cannot know whether the key is attacker-controlled; it is the canonical noise generator and is usually set to warn, not error. *Harvey:* exclude from the free count entirely (Semgrep covers real prototype-pollution/injection with taint context). If ever run, suppress via applicability gate: only a finding when the key is taint-reachable from request input. [ [docs](https://github.com/eslint-community/eslint-plugin-security/blob/main/docs/rules/detect-object-injection.md), [issue #136](https://github.com/eslint-community/eslint-plugin-security/issues/136) ]
- **`detect-non-literal-fs-filename` / `detect-child-process`** — fire on any non-literal argument to an `fs`/`child_process` method, and even misfire on *unrelated* methods named `.open()`/`.exists()` (e.g. a lodash `_.exists`, a React `onClick={() => this.open(item)}`, or `fs.writeFile` passed to `util.promisify`). Benign for static/derived-safe paths and for name collisions with non-fs APIs. *Harvey:* drop from free count; require taint-from-request + confirmed `fs`/`child_process` receiver before flagging. [ [issue #26](https://github.com/nodesecurity/eslint-plugin-security/issues/26), [issue #54](https://github.com/nodesecurity/eslint-plugin-security/issues/54), [issue #13](https://github.com/nodesecurity/eslint-plugin-security/issues/13) ]
- **Engine caveat:** the plugin crashes on ESLint 9 flat config until patched (already noted in `mechanical-toolchain.md` §5).

### A.2 — SonarQube (JS/TS, Community Build)

- **`S2068` hardcoded-credentials** — flags a string assigned to any variable whose *name* contains `password`/`secret`/`token`, even when the value is not a credential: empty-string initializers (`_password = ""`), UI labels (`passwordQuestion = "What is your favorite color"`), or Supabase-app names like `password_label`, `awaiting_password_reset`, `resetPasswordUrl`. Sonar itself says it "makes a best effort and lets a human auditor sort it out" — i.e. it accepts FPs by design. *Harvey:* never count a secret finding on *name* alone; require the value to match a provider key pattern or pass an entropy+verification gate (TruffleHog `--only-verified`). [ [Sonar community](https://community.sonarsource.com/t/false-positive-for-password-detected-in-this-expression-review-this-potentially-hard-coded-credential/32964), [sonar-dotnet #7914](https://github.com/SonarSource/sonar-dotnet/issues/7914) ]
- **`S5852` / `S2631` ReDoS** — flags any hardcoded regex containing ≥2 quantifiers (`*`, `+`, `{`, `.`), a deliberately wide net raised as a Security *Hotspot* (review-required, not confirmed). Benign for linear-time patterns that use negated character classes / bounded matching, e.g. the ubiquitous email check `^[^\s@]+@[^\s@]+\.[^\s@]+$`. *Harvey:* exclude ReDoS from the mechanical count; it needs actual backtracking analysis, so route to review tier. [ [Sonar community](https://community.sonarsource.com/t/false-positive-regex-dos-vulnerability/102019), [FPs S5852](https://community.sonarsource.com/t/fps-security-hotspot-s5852-polynomial-runtime-regex/76316) ]
- **`S4790` weak-hash (MD5/SHA-1)** — flags MD5/SHA-1 use in *any* context. Benign for non-security uses: a cache key, an ETag, a checksum/dedup fingerprint (a very common Next.js pattern for cache-tag hashing). Sonar does not reliably honor a "not for security" signal. *Harvey:* only a finding when the hash output flows into an auth/integrity/password/signature sink; a hash used as a `unstable_cache` tag or ETag is benign. [ [Sonar community FP md5](https://community.sonarsource.com/t/make-sure-this-weak-hash-algorithm-is-not-used-in-a-sensitive-context-here-false-positive-with-md5/152193), [S4790 usedforsecurity](https://community.sonarsource.com/t/s4790-support-usedforsecurity-false/119453) ]
- **`S6479` array-index-as-JSX-key** — flags `key={index}`, but also over-fires on *composite* stable keys like `key={`${item.id}-${index}`}` which are safe. Plus the React/quality-noise set already named in `mechanical-toolchain.md` §1: `S3776` (cognitive complexity over-fires on functional components), `S1481`/`S1854` (unused/dead — duplicates ESLint), `Web:S6853` (label association). *Harvey:* all quality/React-FP rules stay out of the *security* count (they are quality-tier at most). [ [Sonar community S6479](https://community.sonarsource.com/t/typescript-s6479-fails-to-account-for-keys-that-include-other-values-with-an-index/107623) ]

### A.3 — Semgrep OSS registry packs

- **`typescript.react.security.audit.react-dangerouslySetInnerHTML`** — an `.audit.` rule (for human auditors, inherently noisy — `mechanical-toolchain.md` §2 says exclude `.audit.*` from the count). It flags `dangerouslySetInnerHTML` even when fed a **constant** or an already-`DOMPurify.sanitize()`-ed value, because single-file analysis can't see the sanitizer. *Harvey:* use the custom `harvey-dangerously-set-inner-html` rule instead, and gate it — a constant literal `__html` or a value returning from a known sanitizer (`DOMPurify.sanitize`, `sanitizeHtml`) is benign; only a taint-reachable non-constant is a finding. [ [semgrep-rules #2168](https://github.com/semgrep/semgrep-rules/issues/2168), [rule](https://semgrep.dev/r?q=typescript.react.security.audit.react-dangerouslysetinnerhtml) ]
- **SQL-injection taint rules (`p/sql-injection`, `p/security-audit`)** — can flag **parameterized / ORM** queries as SQLi: a query built with `setParameter(...)`/`$1` placeholders, or assembled via a `StringBuilder`/query-builder where the tainted-looking variable is actually bound safely. OSS single-file taint also mis-identifies safe APIs. *Harvey:* a `pool.query(sql, [params])` call using `$n` placeholders (no template-literal interpolation of request data into the SQL string) is benign — the true-positive shape is string **concatenation/interpolation** of untrusted input into the query text. [ [GitLab #471655](https://gitlab.com/gitlab-org/gitlab/-/issues/471655), [Semgrep #10977](https://github.com/semgrep/semgrep/issues/10977), [SQLi ruleset](https://registry.semgrep.dev/ruleset/sql-injection) ]
- **General:** OSS engine is single-file, intraprocedural taint only; MEDIUM/LOW-confidence + `.audit.*` rules are triage-only (`mechanical-toolchain.md` §2). Only HIGH-confidence, ERROR-severity, non-audit rules feed the count.

### A.4 — Generic secret scanners (gitleaks / TruffleHog / entropy scanners)

- **Supabase `anon` (publishable) key in `NEXT_PUBLIC_SUPABASE_ANON_KEY`** — **public by design.** The anon key is meant to ship in browser code; it grants only what RLS policies allow. Critically, anon and service-role JWTs are *structurally identical* (both `eyJ…`), so a shape/entropy scanner flags both. *Harvey:* this is the single most important secret-scanner FP for our audience — never flag the anon key. Distinguish by **decoding the `role` claim** (`gitleaks --max-decode-depth 2`; `role: anon` → benign, `role: service_role` → Critical), path-allowlist and rule-allowlist `NEXT_PUBLIC_SUPABASE_ANON_KEY` (already the plan in `mechanical-toolchain.md` §3). [ [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys), [Securing your data](https://supabase.com/docs/guides/database/secure-data) ]
- **`.env.example` / sample-config placeholders** — `your_api_key_here`, `sk-xxxx…`, `changeme` are documentation, not secrets; low-entropy placeholders pass, but higher-entropy dummy values (and empty-string `PASSWORD=` examples) still trip entropy rules. *Harvey:* path-allowlist `.env.example`, `*.sample`, `*.template`, docs/fixtures; require live verification (TruffleHog `--only-verified`) before counting. [ [gitleaks #1830](https://github.com/gitleaks/gitleaks/issues/1830), [gitleaks #1828](https://github.com/gitleaks/gitleaks/issues/1828) ]
- **Entropy-only hits on non-secrets** — gitleaks entropy detection flags plaintext variable names, hashes, UUIDs, base64 blobs, and JWT-shaped anon tokens with no verification. *Harvey:* count only verified secrets or custom-pattern matches (mechanical-toolchain.md §3 verdict); raw entropy → triage. [ [gitleaks #1830](https://github.com/gitleaks/gitleaks/issues/1830) ]

### A.5 — Dependency scanners (`npm audit`)

- **Dev-dependency / non-reachable transitive noise** — `npm audit` applies the same severity label regardless of whether the code runs at build, test, or production runtime; build-time tools (webpack, babel, eslint) get flagged "CRITICAL" though they never execute in prod, and a typical project shows 10-30 transitive "vulnerabilities" with no reachable path. *Harvey:* only an **exact match on a specific known-critical CVE with a confirmed version range** (e.g. `next` in the CVE-2025-29927 range) is trustworthy for the count (`mechanical-toolchain.md` §4); dev-only and generic transitive findings are triage/informational. Note the exploitability caveat (CVE-2025-29927 only matters self-hosted with middleware auth). [ [overreacted: npm audit broken](https://overreacted.io/npm-audit-broken-by-design/), [pkgpulse](https://www.pkgpulse.com/guides/why-npm-audit-is-broken) ]

**Secondary manifest fixtures (`[B2-deferred]` layout decision).** The seven rows above needed a manifest state that conflicts with the main target's single root `package.json` (one `next` version, a committed lockfile). They live in two STANDALONE project-root fixtures under `targets/calibration/fixtures/`: `legacy-app/` (EOL next, vulnerable react-dom, critical minimist, IOC `flatmap-stream`, no lockfile) and `supported-app/` (supported next, patched react-dom, a legit-postinstall dep, committed lockfile) — each a root, not a monorepo sub-package (whose missing lockfile the root's would otherwise cover). The product scanner (`runMechanicalScan`) is unchanged (root-only manifest + root-scoped lockfile check, no monorepo FP); the calibration runner (`validate-calibration.ts`) additionally scans each fixture root with the offline manifest checks (`checkNextVersionCVEs`, `checkKnownDependencyCVEs`, `checkKnownIoc`, `checkLockfilePresence`), location-labelled `fixtures/<app>/…`. Network/binary passes are not re-run on fixtures. `flatmap-stream` is data only — never installed. See GROUND-TRUTH.md §B2 for the full write-up.
