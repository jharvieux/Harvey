# fp-rules — triage exclusions for the multi-tenant Supabase/Next.js scan
#
# Pass to the reference harness triage:
#   /triage VULN-FINDINGS.json --fp-rules briefs/fp-rules.txt
#
# These suppress the known false-positive classes so the report is high-signal.
# A scanner that flags these wastes the client's trust. Each rule says when NOT
# to flag — and, importantly, the narrow condition under which it IS still a finding.

## Service-role / RLS

- SERVICE-ROLE BYPASS IS NOT A FINDING BY ITSELF. Server-side jobs, crons, and
  trusted internal code legitimately use the service-role client to bypass RLS.
  Only flag when the service-role path is (a) reachable from untrusted input
  (user text, webhook body, an LLM tool call that builds a query), or (b) the
  service-role key is exposed to the client/edge or a URL.

- RLS-ENABLED-NO-POLICY ON A SERVICE-ROLE-ONLY TABLE IS SAFE BY DESIGN. RLS on
  with zero policies is deny-all to anon/authenticated. Note it; do not flag as a
  vulnerability. (Contrast: RLS OFF with no policy IS exposed — that's a real finding.)

## Counters / concurrency

- DERIVED ABSOLUTE VALUE IS NOT AN RMW RACE. `.update({ status: 'done' })` or a
  field set to a freshly computed absolute value (not `stored_value ± n` read from
  a prior SELECT) is not a read-modify-write race. Only flag when the new value is
  computed FROM a previously read copy of the same counter/balance column.

## URL validation

- OPERATOR / ENV CONFIG URLS ARE EXEMPT. `z.string().url()` (or no validation) on
  a trusted operator-supplied env/config value — which may be non-http like
  `redis://` or `postgres://` — is fine. Only flag USER-ingested, persisted, or
  rendered `*_url` fields (source_url, image_url, avatar_url, webhook_url, etc.).

## Permission gates

- A SHARED PERMISSION GATE IS ONLY A FINDING IF THE ACTIONS DIFFER. Reusing one
  gate across a route is fine when every action behind it requires the same
  authority. Only flag when a single gate covers actions with DIFFERENT authority
  requirements (e.g. read + delete behind one check).

## Rate limiting

- IN-PROCESS CACHES ARE NOT LIMITERS. A module-level `Map`/`Set` used as a CACHE
  (memoization, dedup, lookup) is fine. Only flag when the structure is acting as a
  RATE LIMIT / QUOTA / THROTTLE (name or usage reads like rate/limit/attempt/
  bucket/quota/hits and it gates request admission).

## Webhooks

- REPLAY PROTECTION MAY LIVE UPSTREAM. Before flagging a webhook handler for
  missing replay defense, check whether protection lives in an imported shared
  handler, middleware, or the provider SDK (Stripe `constructEvent` enforces a
  timestamp window). Only flag when no replay signal exists anywhere in the path.

## Scope

- TEST / FIXTURE / SEED / DEV-SCRIPT CODE IS OUT OF SCOPE. Findings in `*.test.*`,
  `__tests__`, `fixtures/`, `seed`/`scripts` that never ship, and storybook/mocks —
  downgrade to informational or drop. The audit is about SHIPPED application code
  (the request path, migrations/policies, server routes).

## General

- AN INTENTIONAL, DOCUMENTED EXCEPTION IS NOT A FINDING. If the code carries an
  explicit inline justification (an allow-comment with a reason) for a flagged
  pattern, treat it as accepted risk — note it in an appendix, don't headline it.

## Secret scanning (mechanical layer — calibration corpus #52/#61)

- THE SUPABASE ANON / PUBLISHABLE KEY IS PUBLIC BY DESIGN — NEVER A FINDING. It
  ships in browser code and grants only what RLS allows. anon and service_role
  JWTs are structurally identical, so distinguish by the DECODED `role` claim:
  `role: anon` → benign, `role: service_role` → Critical. Suppress the anon key BY
  ITS OWN VALUE, never by what else shares the line: the gitleaks allowlist is
  regexTarget=match, and the residual `jwt` hit on the raw token is cleared by the
  decoded role claim in secrets.ts. A line-level suppression (what this brief used
  to prescribe) deletes a real secret that merely sits on the same line — MEASURED
  2026-07-26, a live-shaped `sk_live_` next to `pk_test_` was reported nowhere (#1078).

- PLACEHOLDER SECRETS IN SAMPLE FILES ARE NOT FINDINGS, BUT THE COUNT IS STATED.
  `.env.example`, `*.sample`, `*.template`, and documented fixtures hold docs, not
  credentials (`your_key_here`, `changeme`, empty `PASSWORD=`). Do not grade them;
  require live verification (TruffleHog `--only-verified`) before counting a
  real-looking value elsewhere. Report how many were skipped and where
  (SEC-GL-ALLOW-00) — a real value committed to a template file is a known leak
  class, and a suppression that leaves no trace reads as a clean result.

- A SECRET IS NOT A FINDING ON VARIABLE NAME ALONE. A value is only a credential
  if it matches a provider key pattern or passes entropy+verification. A variable
  merely NAMED like one (`passwordLabel`, `awaiting_password_reset`, `secretQuestion`)
  holding a UI string is benign (vs name-only detectors like Sonar S2068).

## Reachability is the WRONG test for presence-based classes (#53/#1302)

- A COMMITTED CREDENTIAL IS A FINDING WHETHER OR NOT ANY CODE IMPORTS THE FILE.
  The dead-code/unreachable-code exclusion — and the standing "TRUE_POSITIVE
  requires the path be reachable from untrusted input" bar — are REACHABILITY
  tests. The classes below are PRESENCE-based: the harm is that the value is in
  the repository and in its history, readable by everyone with repo access, and
  it stays compromised after the file is deleted. "Nothing imports it today" is
  one refactor away from false, and is not what makes the credential exposed.
  RECORDED 2026-07-09 (#53), on this repo's own calibration target: the triage
  verifier dropped the genuine hardcoded `service_role` JWT in `lib/admin.js`
  because nothing imports that file. RE-MEASURED 2026-07-28 (#1302) against a
  clean fixture — an unimported `service_role` JWT in a file whose path carries
  no test/fixture marker — with the real verifier prompt and NO org rules
  loaded: 3 of 3 independent verifiers returned TRUE_POSITIVE, each reasoning
  unprompted that presence is not reachability. So the drop does NOT reproduce
  on demand, and this rule STATES A CONTRACT rather than repairing a live
  regression. It is written anyway because 3 votes on one fixture on one day is
  weak evidence of absence, and because #53's file sat in `targets/calibration/`
  — where the example/fixture clause of the same exclusion applies for an
  independent and legitimate reason, which is a confound #53 did not separate.

  The presence-based classes, exhaustively — this list does NOT generalize to
  other finding types:
    1. a hardcoded credential, API key, token, private key, or a connection
       string carrying a password, in any committed file;
    2. a REAL credential committed to a sample/template file — the placeholder
       rule above exempts PLACEHOLDERS (`your_key_here`, `changeme`), never a
       live value;
    3. a credential in committed build output, a bundle, or a lockfile;
    4. a credential in git history that no longer exists in the working tree.

  For these four, the verdict turns ONLY on whether the value is a live
  credential (provider key pattern, decoded `role` claim, entropy+verification
  per the rules above) — never on whether a call path reaches it. Specifically:
    - do NOT cite the test/dead/example-code exclusion or the
      missing-hardening-with-no-exploit-path exclusion against them;
    - do NOT require a caller or a first call-site link; record it as not
      applicable and say the class is presence-based;
    - the out-of-scope rule for test/fixture/seed/dev-script code above governs
      that code's OWN defects; it does not make a live credential committed
      there unreported.

  Everything else keeps the reachability exclusions exactly as they are — an
  unexploitable crash in dead code, or an injection sink no input reaches, is
  still a false positive. This rule narrows one exclusion for one class of harm;
  it does not weaken triage generally.

## SQL / query construction

- A PARAMETERIZED QUERY IS NOT SQL INJECTION. `pool.query("… where x = $1", [val])`
  binds the untrusted value as a parameter — it never enters the SQL text. Only flag
  string CONCATENATION / template-literal INTERPOLATION of untrusted input into the
  query string (the P-SQLI-CONCAT shape).

## XSS / dangerouslySetInnerHTML

- SANITIZED OR CONSTANT `dangerouslySetInnerHTML` IS NOT A FINDING. `__html` fed a
  string literal, or a value returned from a known sanitizer (`DOMPurify.sanitize`,
  `sanitizeHtml`), is benign — single-file SAST FPs here. Only a value tainted from
  request input reaching `__html` unsanitized is a finding.

## Quality-rule noise (never in the SECURITY count)

- BENIGN `obj[key]` BRACKET ACCESS on a hardcoded/enum-validated key is not
  injection (vs eslint detect-object-injection). Composite/stable JSX keys
  (`${item.id}-${index}`) are not a bug (vs Sonar S6479). A LINEAR regex with negated
  classes (`^[^\s@]+@[^\s@]+\.[^\s@]+$`) is not ReDoS (vs Sonar S5852). MD5/SHA-1 used
  as a cache key / ETag / dedup fingerprint is not a weak-crypto finding unless the
  hash flows into an auth/integrity/password/signature sink (vs Sonar S4790). A
  STATIC/derived-safe `fs` path or a non-fs method that merely happens to be named
  `.open()`/`.exists()` is not a finding (vs eslint fs/child_process rules).

## Dependencies

- A DEV-ONLY VULNERABLE DEPENDENCY IS NOT A FREE-COUNT FINDING. Build/test-chain
  tools (webpack, babel, eslint plugins) in `devDependencies` don't run in prod;
  downgrade to informational. Only an exact known-critical CVE on a runtime dep with
  a confirmed version range is trustworthy for the count.
