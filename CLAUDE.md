## The audit — full scope, how to run it, and the coverage guard

**This is a COMPLETE codebase-health audit, not a security scan.** All ten modules (M1–M10) carry **equal weight** in the deliverable — none is the "lead," none is secondary, and none may be prioritized over the others when executing. Running a security-only (or any ad-hoc) subset — or scoping any single module's run to only its security-relevant portion — is a defect; it has happened, don't repeat it. Every engagement accounts for all ten modules against every enumerated target. Authoritative scope: `briefs/audit-modules.md`.

**The bias survives the run — guard the JUDGMENT, not just the scope.** Everything above governs which modules *execute*. The recurring failure is one layer down: executing all ten and then **narrating, ranking, or deciding** through a security lens. It has now happened three times with the full set running correctly each time — findings synthesis (2026-07-12), GTM framing (2026-07-21), and an M4 scoping call (2026-07-26) argued down with "a lot of low-stakes rows in a security-weighted report". **There is no security report.** The tell is dismissive vocabulary attached to a non-M1 finding: *low-stakes*, *maintainability-only*, *just a nit*, *cosmetic*, *noise*. When volume genuinely is the objection, the answer is a threshold or a disclosed rollup (#935's shape) — never demoting a module's band. An M4 duplicate and an M8 untested branch are the deliverable, not garnish on it.

### The coverage guard — never silently skip a module

Completeness is a core product principle: **a module that cannot run is recorded as `partial` / `requires-live-run` WITH THE REASON — never silently omitted. Fail loud.**

**Silent omission is worse than a wrong status.** A `missed` shows up in the tally; an absent row does not. If a thing cannot be assessed, say so IN THE OUTPUT — an unstated limitation reads as a clean bill of health. (`requires-live-run: 0` once asserted nothing awaited a live run while four planted bugs were simply not listed — #345.)

**Scope decisions that are DISCLOSED, not silent (#903):** infrastructure code (Dockerfiles, Compose, Terraform, K8s/Helm) is out of scope BY DECISION — rationale in `docs/design/infrastructure-out-of-scope.md` — and a target containing it gets an `INFRA-SCOPE-00` not-assessed row naming what was found and its file counts, never silence. **Every `src/cli` entry point that exits non-zero imports `./sync-stdio.js` as its FIRST import (#1768, 2026-07-31).** Node writes to a FILE synchronously and to a PIPE asynchronously, and `process.exit()` does not drain the async queue — so on every CI step, every `| tee` and every `spawn(…, stdio: "pipe")`, the LAST thing a CLI prints can be discarded. What these CLIs print last is a gate's verdict line or an export's refusal banner, sitting immediately before `process.exit(1)`; an exit 1 whose reason was thrown away is indistinguishable from a crash. MEASURED 2026-07-31, spawned as the harness does: marker lost 5/5 runs without the guard, 0/5 with it. `sync-stdio.test.ts` proves it through a real process in both directions and holds a discovery-backed ratchet, so a NEW exiting CLI fails until it imports the guard — add the import rather than editing the ratchet. `args.ts` is excluded as a library (imported by 10 CLIs, entry point of none) and is covered transitively; the exclusion is a named constant, so a file that stops being a library fails loud. **#1758 recurred twice more before the guard landed (2026-08-01T00:03:07Z and 00:06:56Z), and #1744's diagnostics attributed it**: the CLI's captured output ends exactly on `validate-calibration.ts:556`'s liveness receipt — the last write before the verdict block — with exit code 1 intact, no stack trace, and the parent resolving on `close`. `import "./sync-stdio.js"` reached that file 59 minutes after the last occurrence; 39 shard-2 jobs since, all green, which at the pre-fix rate would happen by chance about 35% of the time. #1758 stays open pending an operator ruling on the quarantine step, not pending a cause. **Read the older `0/15 tail loss on darwin` figure as history, not as current**: the committed negative control now reproduces the truncation on darwin arm64 on every run measured, and what changed is #1780's reader fix — the earlier control delayed from `spawn()`, so `tsx`'s own boot beat the timer and the parent was already draining when the child wrote. A control that observes nothing and a control that observes no defect print the same zero.

**A timing-anchored test is a flaky test: anchor to the child's FIRST BYTE, never to spawn (#1768, MEASURED 2026-07-31).** That same test file shipped green and then failed **3 runs in 6** on `main`, because its backpressure delay ran from `spawn()` while `tsx` takes 300-600ms to boot — the reader was routinely already draining, so the negative control passed for the wrong reason. If a test's premise is "the reader is slow", make the clock start when there is something to read.

Run it before every push. If it fails, fix and re-verify before pushing. If a failure is pre-existing on `main` (not caused by your branch), call it out and don't block on it.

## Working doctrine (ported from ATC)

- **Simplicity first.** Minimum code that solves the problem. No features beyond what was asked, no abstractions for single-use code.
- **Surgical changes.** Don't refactor what isn't broken; match existing style.
- **Slop sweep before commit.** Re-read your own diff and delete: comments that say WHAT instead of WHY, single-call helper functions, try/catch that re-throws or swallows, JSDoc paragraphs on simple functions, TODOs without an owner or issue ref, defensive validation of inputs that can't be invalid.
- **Tests verify intent, not just behavior.** A test that can't fail when business logic changes is wrong.
- **Never leave a known bug or deferral untracked.** Trivial: fix inline. Non-trivial: open a GitHub issue before the session ends, specific enough that someone returning cold can pick it up.
- **Fail loud.** "Done" is wrong if anything was skipped silently. Silent omission is worse than a wrong status — an absent row never appears in a tally, so it cannot be argued with. If something could not be assessed, say so in the output.
- **Accounted for is not delivered.** A ledger row, a COVERAGE PASS and an exit 0 prove a module was ACCOUNTED FOR — they never prove its findings REACHED THE DELIVERABLE. A whole recurring defect class lives in that gap (#1040/#1043/#1045/#1050/#1061/#1062/#1101): the detector works, the finding is dropped at a producer→consumer seam, every status reads clean. So when you add or change a detector, follow its output all the way to the assembled document, and read "the tally is fine" as a statement about bookkeeping only. The mechanism that enforces this is `pnpm exec tsx src/cli/validate-conservation.ts` (#1064/#1097) — a planted finding per module, asserted both PRODUCED by that module's own probe and PRESENT in the assembled deliverable, with zero findings for a planted defect a FAIL. It needs the mechanical binaries, so it is not part of `pnpm verify`; its logic is, via `src/audit-conservation.test.ts` — its wiring test moved out too (#1105), gated behind `HARVEY_CONSERVATION_E2E` and run isolated in `.github/workflows/conservation.yml`.
- **A claim you INHERITED deserves the test you would give a claim you are auditing (2026-07-30).** The re-test doctrine below switches off, reliably, the moment a claim arrives as *context* rather than as something you went looking for. Issue bodies, PR bodies, code comments and your own supervisor's brief are all claims. Three from one day: a sweep spent hours falsifying other people's recorded reasons while relaying *"the free scan is sold as instant"* — a phrase that exists in NO source file or doc, invented in an issue comment, repeated into a status report, then written into `SESSION.md` as the premise of a decision put to the operator, tested by nobody across four hops and refutable by one grep (the promise is *"Same-day turnaround"* / *"report emailed within 24h"*; the only "instant" copy is about the QUOTE). The same day, a supervisor-written issue body named a symbol that did not exist on `main` and implied a fix had landed when it was on an open PR; and a PR body asserted its seeded sample ids were listed in an issue that listed five examples. **Two documents citing one guess is not corroboration — and neither is a brief citing an issue citing a comment.**
- **Verification is the highest-yield step in the process, not a formality (2026-07-30).** Every PR that closes an issue gets an INDEPENDENT acceptance verifier — never the executor that wrote it, never a fix agent from the same PR. On the day this was measured it found something in nearly every PR, including green, well-tested ones, and CI caught none of it: a negative control guarding a function with **no production caller** (reverting the shipping line left all 47 tests green); a figure tagged MEASURED computed with a **different predicate than the code** (48/384, not 54/390); a client-facing criterion — *"a visitor can request the PDF and receive it"* — where only "the code exists and built locally" was true; a merge instruction from the SUPERVISOR that was wrong and would have downgraded a fixture; and a PR body pointing at evidence that did not exist. Its verdict is `met` / `partial` / `unmet` per stated criterion with a file:line or test name — *"looks correct"* is not evidence — and a `partial` splits or stays open rather than closing.
- **A sample without its draw is not reproducible, and a limit without its population is a guess (#1345, 2026-07-30).** State the population BEFORE auditing, and publish the drawn ids, not just the seed: `random.seed(N)` with no committed ordering or sample call is a claim about the past. The population is often the finding — one audit's whole premise ("PR review comments are plausibly the densest seam") had a population of **zero**, 0 review comments across 618 merged PRs; a corpus had a population of zero for both shapes a fix targeted, which is what made planting fixtures necessary rather than optional; and a bound audited on 2026-07-27 had never occurred in 60 PRs. Where reading the whole population is impractical, a seeded stratified sample with a Wilson interval is the accepted form — the M5 seam exemption's recall cost was settled that way (50 of 653 read, 10% wrongly spared, CI [4.3%, 21.4%]).
- **"Not required" is not "not important" (2026-07-30).** A non-required check that FAILS, or that could not run, still has to be read. `corpus-drift` **was not** a required context — it died at setup for days, reported nothing distinguishable from a clean run, and a PR merged on three green required checks while the gate measuring its blast radius had never executed: 653 findings silently suppressed and a live regression on `main`. It has since been registered as required (2026-07-30), so the specific hole is closed — **but do not read the fix as retiring the rule.** The lesson was never about that one gate: it is that GREEN and EXECUTED are different facts, and a check which cannot run reports the same colour as one that ran clean. Promoting a gate to required does not change that; it only makes the silence blocking. Before merging on green, ask which gates actually EXECUTED — read the step list, not the rollup (`gh run view <id> --json jobs`, and prefer a job that asserts it reached its own measuring phase, the #1561 gate-liveness shape). All four of those non-required checks — `heavy CLI tests`, `disclosure-venue`, `alert-paths`, `acceptance` — now emit a gate-liveness receipt naming how many units they scored and assert it before they may be green (#1568), so "did it EXECUTE" is answerable from the job summary rather than by reading the step list. The rule stands regardless: a green rollup is still not proof, and a check that could not run still reports the same colour as one that ran clean. **And REQUIRED does not mean EXECUTED either (#1830, 2026-08-01).** PR #1826 changed one line of `.github/workflows/reasons-drift.yml`; its `verify` job — a required context — reported `success` after running exactly three steps (`Set up job`, `Gate on required jobs`, `Complete job`): no checkout, no install, no vitest. The `changes` path filter classified a workflows-only diff as touching nothing relevant and short-circuited to a green no-op, while `src/mechanical-binaries-cache.test.ts` GLOBS `.github/workflows/` as its input and asserts an exact consumer list. `main` went red on the merge with all four required contexts green on the PR. The filter's model of relevance and a test's actual input set can disagree, and nothing reconciles them — so "it's required" is not a substitute for reading the step list, it is the case where people stop reading it.

- **Never present a guess as fact.** Flag uncertainty before the claim, especially for library/API behavior and version-specific syntax.
- **Verify the defect before you fix it — this is a step with an output, not a posture.** Before writing code against an issue, a recorded blocker, or a `not-run` reason: read the current code, run the failing case or reproduce the symptom, and check `git log` on the touched paths for work that landed after the claim was written. State in the PR body what you verified and how. Already fixed → do NOT re-implement: close it with a comment naming the fixing commit/PR. Misdiagnosed but a real adjacent defect exists → fix that and correct the record. **A `grep` that returns nothing is not proof of absence (2026-07-30).** A source file containing a literal NUL byte is classified as BINARY, and plain `grep` silently returns nothing and exits 1 for the WHOLE file. Two tracked files were in that state until 2026-07-30, and a false-decline audit read the resulting zero as "no production caller" when the symbol had **five** call sites — corrupting that audit while it ran. Grepping the tree is this repo's primary re-test primitive, so a silent skip manufactures exactly the false declines the doctrine exists to catch. `src/greppable-sources.test.ts` now fails loud on a new one; when a zero is load-bearing, confirm with `grep -a` or `git grep`. Convention and rationale in `docs/design/recorded-reasons.md`. A live-tier falsifier names any out-of-repo target as a placeholder bound from `HARVEY_FALSIFIER_<NAME>`, never bare `<angle-brackets>` — those reach the shell as an input redirect, exit non-zero, and read as "the blocker still holds", which is how all five live falsifiers sat green while re-testing nothing (#1246). For the same reason a lookup that CANNOT run (no credential, no network) must exit 127 = UNVERIFIABLE and fail the gate, never non-zero = still-blocked. And a falsifier that RUNS cleanly can still be incapable of firing — a case-sensitive `grep -q CLOSED` over an API answering lowercase `closed` exits 1 in BOTH directions, and sat inside a green `--revalidate` run re-testing nothing (found 2026-07-27, #1345). **So EXERCISE every falsifier in both directions before recording it**: run it as committed, then against a state where the blocker is gone, and show both exit codes. A falsifier nobody has watched exit 0 is indistinguishable from one that cannot): an **empirical** reason is re-testable against the world and MUST carry the command that would falsify it — **written so the command EXITS 0 WHEN THE BLOCKER IS GONE** — while a **decisional** reason awaits a human ruling and must NOT carry one (re-testing a product ruling is a category error; the gate refuses it). A reason with no falsifier is unfalsifiable and therefore permanent. `pnpm exec tsx src/cli/validate-reasons.ts` checks the structure (also enforced under `pnpm verify` by `src/recorded-reasons.test.ts`); `--revalidate` re-runs every empirical falsifier and fails loud on any that now succeeds. Prefer phrasing an untested blocker as a question ("does the token store expose non-owner reads?") over an assertion ("token identity is unreachable") — a question invites the next person to test it, an assertion closes the file. And never let a claim launder itself by being copied: two documents citing one guess is not corroboration — the #1033 sweep found that exact shape twice more (§8 classes 1/2/5 "no detector" in `fix-implementation.md` + `fix-calibration-acceptance.md`, and F-11 "no static detector at all" in `superredhat-recall-measurement.md` + `src/scan/semantic-corpus.ts`), both false, both corrected.
- **A budget limit must not borrow impossibility's vocabulary (#1319/#1326).** *"Out of budget"* and *"out of reach"* are claims about your afternoon; *"cannot"*, *"impossible"*, *"structurally cannot"* are claims about the world. Four recorded blockers spent the second register on the first situation and all four were false — #951's *"a full pull is out of budget"* (the next executor pulled the whole stack and shipped a merged live proof 26 minutes later, and the capture found a real bug the guess never would have), #957's *"genuinely out of reach for a mechanical assembly"* (98 lines, 3h25m later, no new dependency), #52's *"correctly NOT mechanically detectable"* (this repo has since built detectors for all three named classes — and the two spec documents still forbidding them were corrected on 2026-07-31, #1375, twenty-two days after the detectors shipped) and #873's *"our mechanical tier structurally cannot see that shape"* (`buildImportGraph` had shipped a week earlier and M9 already used it). A budget claim invites the next person to just do it; an impossibility claim closes the file — and closes it silently, because by construction nobody exercises a path recorded as foreclosed. So if the constraint is time, say time: *"not attempted this round; the pull is ~20s, the stand-up is documented in X."* Reserve cannot/impossible/out of reach for what you have tested. The reason registry enforces the half it can reach — impossibility vocabulary in a `REASON:` tagged ASSUMED is a structural error under `pnpm validate-reasons`, with negative controls at both the unit and CLI layers. PR bodies are reachable by no gate and stay doctrine.
- **A supervised path produces a RELAY, not a silent close (#1319/#1326).** No executor has ever recorded *"asked the operator, was refused"* — while grants are routine and on the record (#1141 carries a verbatim *"Workflow changed approved"*, #1205 promoted a check to required, #1216 moved a watch into CI). Yet *"that path is supervised"* silently terminated acceptance criteria in #945 (*"the gate runs in CI"* — unmet, unmentioned), #1056, #472 (a CLAUDE.md line the criterion named, never relayed) and #381, where the criterion asked only for a flag with proposed wording and even that was skipped, while the same PR performed it correctly for a sibling issue. **A supervised path stops the EDIT, never the CRITERION**: record the operator question on the issue with the exact wording you propose, and name it in the PR body and in your report. The reason registry enforces its slice — a `REASON:` citing a supervised path as its blocker must be decisional with a `DECISION:` naming where the operator was asked. **The supervisor's mirror of this rule: do not TIGHTEN an operator grant in a downstream brief without saying so.** On 2026-07-28 a sweep supervisor excluded `docs/runbooks/**` from a granted docs permission and blanket-banned targets the operator had authorised, and two of #1299's acceptance criteria were reported blocked as a result — a self-imposed restriction is indistinguishable, in the record, from a real blocker.
- **Disclosure is the second-best outcome, and it is EARNED BY AN ATTEMPT (#1345, operator ruling 2026-07-27).** A not-assessed row is the right answer when something genuinely cannot be assessed — silence is always worse, and the disclosure-row family exists for exactly that. But it is a **fallback, never a first move: you may not disclose what you have not tried.** Before writing that something cannot be done, spend the attempt and record what you actually ran. Three tests every disclosure must pass. (1) **Provenance** — MEASURED or TRIED, never ASSUMED wearing MEASURED's register. (2) **Population** — how many real cases hit this limit? A bound audited on 2026-07-27 had never occurred in 60 PRs; **a limit with a population of zero is not a limit, it is a guess.** (3) **Scope** — one failed attempt does not license a universal claim ("no keyword-overlap rule can accept a paraphrase" — one variant tried, five more existed). If you cannot pass all three you have not found a limitation, you have run out of afternoon: say *that* instead. The 2026-07-27 audit of 677 closed issues found the dominant failure was never "documented instead of built" — the code usually shipped — it was **a false reason attached to the undone half**, which is worse, because the shipped half makes the closure look legitimate and nobody re-tests the decline. Instances: #1204 ("the headers are checked by their effect" — a bare Express app produced ZERO findings), #1231 ("a lifecycle script only ever exists in a manifest" — npm lockfiles record `hasInstallScript` per resolved package), #370 (declined cross-file counting for want of a module graph; `buildImportGraph` had shipped four days earlier in the same directory), #266 ("M6 is not mechanically detectable" — `pnpm detector-census` measures 33 M6 detectors, first five landing 24h later), #556 ("`package.json` is supervised" — verified against `CLAUDE.md` as it stood that day: **the constraint never existed**), #1310/#1312 (2026-07-31 — `TargetProfile.privilegedRpcs` was documented "DB-derived" while `src/cli/pentest.ts` passed a hardcoded `[]`, so the Critical ANON-PRIVILEGED-RPC replay answered "No anon-executable privileged RPCs discovered" on EVERY target it ever ran against; wiring it exposed a second layer, a 2xx-only predicate that scored `cleared` while the planted `issue_refund` had demonstrably executed — the strongest argument in this file for running the stack before triaging against it), #1012 ("registry packs need a network fetch, so deliberately not resolvable" — online it resolves in ~1.4-2.2s; the unmeasured cost was that a share of a real deliverable's rule findings could never be marked resolved — **CLOSED by #1368** 2026-07-30, which wired the replay online. Note the re-measure was itself corrected in review: the share is **48 of 384 rule-id-shaped findings (12.5%)** under the code's own `REGISTRY_RULE_SHAPE`, not the 54/390 first recorded with a bare dot predicate — a number tagged MEASURED that used a different predicate than the code, inside the fix for a false claim).
- **"Closed in favour of" is how a real gap loses its tracker (#344, 2026-07-27).** #344 said M6 is sold in the ten-module deliverable and measured by nothing. It was closed as a near-duplicate of #267 — whose acceptance criteria were all genuinely met and never mentioned M6. Twelve days on M6 still had **zero** entries (`ls src/scan/calibration/*.entries.ts` — run it, never quote a count from here). #1314 settled it on 2026-07-28 by DISCLOSURE, not by fixtures: M6 rendered as a `0` census row carrying a named substitute gate, so the omission became a stated decision instead of an invisible one, and an exemption a module no longer needs fails loud as STALE. **#1371 then closed the gap itself** (operator ruling 2026-07-28): M6 now has a real scored corpus — 33 indicator classes, 0 uncovered, its own consumer in `src/scan/m6-indicator-corpus.ts` — and #1314's M6 exemption is retired. Read this bullet as the pattern, not the status: the DISCLOSURE and the FIXTURES were two separate pieces of work twelve days apart, and for that whole window "now disclosed" was the honest answer and "M6 now has fixtures" would have been false. No gate catches this: Gate 1 asks whether a PR met the criteria of the issues it closes, and #267's were met. So when you close one issue in favour of another, **the surviving issue must carry the closed one's criteria explicitly** — a comment on a met issue is not a tracker.
- **If your change falsifies a claim in this file, say so — you cannot fix it yourself. THE ORCHESTRATOR APPLIES IT, NOT YOU, AND NOT MID-SWEEP (operator ruling 2026-07-26).** This file is supervised: a dispatched agent must never edit it, **even when the operator has granted CLAUDE.md changes for the session** — a grant authorises the ORCHESTRATOR to make them, it does not delegate down. The flow is: **agent reports the falsified sentence → orchestrator records it in the sweep ledger → orchestrator applies every recorded change in ONE pass, just before the final summary.** Two reasons it works this way. (1) Concurrent executors editing one file collide: on 2026-07-26 six of them edited this file and PRs #1108/#1110 had to be hand-sequenced around the conflict. (2) A sentence "falsified" at 10:00 is often re-falsified by a later batch the same day; batching to the end means the file is corrected once, against the final state, instead of thrashing. So the moment your work makes a sentence here untrue — a "known gap" you closed, a prereq you removed, a command you renamed, a guard you wired or unwired — **name the exact sentence and recommend the replacement wording**, in your PR body AND your report to the supervisor. **The supervisor must relay it to the operator with that recommendation before the session ends — it may not be silently absorbed.** Every dispatched agent reads this file: a false sentence here misinforms every future session, and in sweep #3 an uncommitted-vs-committed drift in this one file caused a class of phantom bugs. #310 falsified its own known-gap paragraph the moment it merged; its executor reported it and it still took an operator question hours later to surface. **A stale CLAUDE.md is not a documentation chore — it is a defect with a blast radius.**
